Week 03

Test Automation

Error, fault, failure — and the first JUnit 5 test.

Rui Maranhão · LDTS · L.EIC014 · FEUP · 2026/2027

Part one

To err is human

Software has bugs.

Why?

Humans write software.

Computers execute it exactly as written.

Three words people use interchangeably, and should not

  • Error — a human action that produces an incorrect result
  • Fault — the incorrect code that action left behind (the “bug”)
  • Failure — the observable wrong behaviour, when the fault is executed

A fault only becomes a failure when it is reached.

Most of testing is the art of reaching things.

Is it a bug, or is it a feature?

Two different questions

Verification

Did we build the product right?

  • Against the specification
  • Internal consistency
  • Tests, reviews, static analysis

Validation

Did we build the right product?

  • Against what the client needs
  • Requires talking to humans
  • Demos, acceptance testing

A program can be perfectly verified and completely useless.

Both questions have to be asked.

Where does the mismatch come from?

Specification vs need

  • The client knows the problem, not the solution
  • The specification is a translation, and translations lose things
  • Small, frequent transformations lose less than one big one
  • This is the argument for iterating — not fashion

Part two

What can I test, and how

What can be tested?

Every development artefact.

Requirements, designs, diagrams, documentation — not only source code.

How do I test?

Three postures

  • As a mathematician — prove correctness against a specification
  • As an accountant — inspect, guided by experience and standards
  • As an engineer — run it enough times

When is enough, enough?

Testing shows the presence, not the absence of bugs.

Edsger W. Dijkstra

Static and dynamic verification are complements.

Reviews find what tests cannot reach. Tests find what reviewers read past.

Part three

Automating it

Suppose you test the game by playing it. What is wrong with that?

Manual testing through the UI

  • Difficult to set up — how do you reach that exact state?
  • Expensive to repeat — a human has to do it again, every time
  • Not reproducible — did you press the same keys?
  • Reports nothing — there is no record afterwards

So we need a tool.

One that stores the tests, runs them, and tells us what happened.

The deal a test framework offers

  • You write what to check
  • It does the plumbing: discovery, setup, isolation, teardown, reporting
  • For each test: set up context → run → assert → tear down
  • In this course: JUnit 5

Your first JUnit 5 test

import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class PositionTest {

    @Test
    void translateMovesByDelta() {
        Position p = new Position(3, 4);

        Position moved = p.translate(1, -2);

        assertEquals(new Position(4, 2), moved);
    }
}

Arrange · Act · Assert. Three blocks, in that order, always.

Lifecycle

class BankTest {
    private Bank bank;

    @BeforeEach void setUp()     { bank = new Bank("International"); }
    @AfterEach  void tearDown()  { bank.close(); }

    @BeforeAll  static void once() { /* expensive, shared setup */ }

    @Test void newBankHasNoAccounts() {
        assertEquals(0, bank.accountCount());
    }
}

@BeforeEach runs before every test. Each test gets a fresh object.

Every test starts from a known state.

If test B only passes when test A ran first, you have two bugs.

Expecting failure

@Test
void depositInWrongCurrencyIsRejected() {
    Account account = bank.open("PT50", Currency.EUR);

    assertThrows(IncorrectCurrencyException.class,
                 () -> account.deposit(Money.of(100, Currency.CHF)));
}

Assert on the exception type, not on a boolean you set in a catch block.

Assertions worth knowing

  • assertEquals, assertNotEquals
  • assertTrue, assertFalse — add a message, or failures are unreadable
  • assertThrows
  • assertAll — report several failures at once instead of stopping at the first
  • assertSame — identity, not equality. Rare, and usually a mistake.

Naming that survives

// what happened?
@Test void test1() { ... }
@Test void testHero() { ... }

// what is guaranteed?
@Test void heroCannotWalkThroughWall() { ... }
@Test void emptyArenaHasNoElements() { ... }

A failing test name should tell you what broke without opening the file.

Where the tests live

  • src/main/java/com/ldts/game/Arena.java
  • src/test/java/com/ldts/game/ArenaTest.java
  • Two trees, same package structure
  • Test code is production code. It gets reviewed, and it gets refactored.

Take away

  • Error → fault → failure: three different things
  • Verification and validation answer different questions
  • Arrange, Act, Assert — one behaviour per test
  • A test that depends on another test is not a test
