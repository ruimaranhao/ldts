Testing Strategies & Coverage

Black box, white box, and what coverage does not tell you.

Rui Maranhão · LDTS · L.EIC014 · FEUP · 2026/2027

Part one

Before you run anything

What is the cheapest defect to fix?

The one found before the code runs.

Reviews and inspections

  • Applicable to every artefact, not just code
  • Driven by a checklist of the errors that actually recur
  • Fagan (1986): inspections detect over 60% of defects
  • The checklist is the point — memory is not a process

What automation does for free

  • Style: a formatter ends the argument permanently
  • Checkstyle, PMD, SpotBugs, Error Prone
  • The compiler warnings you have been ignoring
  • Use them while coding, not the night before delivery

Part two

How much testing is enough

When do you stop testing?

Honest answers

  • When the defect discovery rate flattens out
  • When seeded faults are being found — fault injection
  • When the risk left is smaller than the cost of continuing
  • When time runs out — the usual one, and the worst one

Fault injection asks: how good is my test suite?

Inject known faults, see how many the suite catches. Week 11 turns this into a tool.

Part three

Two ways in

Black box vs white box

Black box

Test against the specification.

  • You see inputs and outputs
  • Survives reimplementation
  • Cannot know what it missed

White box

Test against the implementation.

  • You see the code
  • Can target every branch
  • Breaks when the code is refactored

The same operation, two views

// Specification
//   pop(stack)
//   pre : stack is not empty
//   post: returns and removes the most recently pushed element
//
// Black box test values: empty stack, one element, many elements

// Implementation
//   stack is an ordered set with a top index
//
// White box test values: top == 0, top == capacity, top in between

Part four

White-box coverage

Your tests pass. What fraction of the code did they even execute?

A control flow graph

Coverage criteria are questions about paths through this graph.

Four criteria, increasing in strength

  • Statement — every statement executed at least once
  • Branch — every decision taken both true and false
  • Condition — every atomic condition takes both values
  • Path — every independent path executed

Where statement coverage lies to you

int divide(int a, int b) {
    if (b != 0) {
        return a / b;
    }
    return 0;
}

// one test: divide(10, 2)
//   statement coverage: 3 of 4 lines  -> looks fine
//   branch coverage:    1 of 2        -> the b == 0 case is untested

100% statement coverage does not imply 100% branch coverage.

if (a && b). Branch coverage needs two tests. Condition coverage needs how many?

Decision vs condition

if (a && b) { ... }

// Branch (decision) coverage:  (true,true) and (false,anything)
// Condition coverage:          a true and false; b true and false
// MC/DC:                       each condition shown to independently
//                              affect the outcome

Java short-circuits &&: if a is false, b never evaluates.

Cyclomatic complexity

  • V(G) = decisions + 1
  • The number of independent paths through a method
  • Also: a lower bound on the tests you need for path coverage
  • Also: a decent smell detector. V(G) > 10 in one method is a design problem, not a testing problem.

JaCoCo in the build

plugins { jacoco }

tasks.test { finalizedBy(tasks.jacocoTestReport) }

tasks.jacocoTestReport {
    dependsOn(tasks.test)
    reports { html.required = true; xml.required = true }
}

tasks.jacocoTestCoverageVerification {
    violationRules {
        rule { limit { counter = "BRANCH"; minimum = "0.70".toBigDecimal() } }
    }
}

./gradlew test jacocoTestReport → build/reports/jacoco/test/html/index.html

Coverage is a floor, not a target.

Low coverage proves you are not testing. High coverage proves nothing.

How do I get 100% coverage with a test suite that asserts nothing?

Like this

@Test
void coversEverything() {
    new Arena(10, 10).update();   // executes the code
}                                 // asserts nothing at all

Green. 100%. Worthless. Week 11 is about detecting exactly this.

Part five

Black-box coverage

The method signature is fine(long daysLate). How many inputs are there?

264.

Are they all semantically different? Obviously not.

Equivalence partitioning

  • Split the input domain into non-overlapping sets
  • Within a set, the program should behave the same way
  • Test one value per set
  • The sets come from the specification, not the code

Partitioning a specification

// spec: if (daysLate <= MAX_FINE_PERIOD) fine = daysLate * DAILY_FINE
//       else                             fine = MAX_FINE

// partitions for daysLate
//   [ ..., -1 ]                  invalid    -> what should happen?
//   [ 0 ]                         boundary
//   [ 1 .. MAX_FINE_PERIOD ]      linear fine
//   [ MAX_FINE_PERIOD+1 .. ]      capped fine

Where do defects cluster?

At the edges.

Off-by-one is the most common bug in the profession.

Boundary value analysis

  • For each partition, test the value just inside each edge
  • And the value just outside it
  • And the edge itself
  • For 0 ≤ d ≤ MAX: -1, 0, 1, MAX-1, MAX, MAX+1

Take away

  • Reviews are cheaper than tests; tests are cheaper than users
  • Statement coverage is the weakest criterion — report branch coverage
  • Coverage measures execution, not verification
  • Partition the input domain, then attack the edges
