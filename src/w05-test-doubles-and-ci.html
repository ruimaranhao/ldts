Week 05

Test Doubles & CI

Testing in isolation, and making the suite run without you.

Rui Maranhão · LDTS · L.EIC014 · FEUP · 2026/2027

Part one

Test-first

When can you start testing?

Before the code exists.

The specification is enough.

Why write the test first

  • It forces you to decide what the method promises
  • It forces you to design the interface before the implementation
  • You find out immediately whether the code is testable
  • You are never afraid to change code that has a suite behind it

A test case is an incomplete specification.

One concrete point on a contract you could otherwise only describe in prose.

Design by contract, made executable

// contract for Dictionary.put(key, value)
//   pre  : key != null
//   post : count == old count + 1  (if key was absent)
//          get(key) == value

@Test
void putIncreasesCountWhenKeyIsNew() {
    Dictionary d = new Dictionary();
    d.put("a", 1);

    d.put("b", 2);

    assertEquals(2, d.count());
    assertEquals(2, d.get("b"));
}

Red → Green → Refactor

  • Red — write a failing test. Watch it fail, or you do not know it works.
  • Green — the simplest code that passes
  • Refactor — clean up, suite still green
  • The third step is the one everyone skips and the one that pays

Part two

Types of tests

What is the best strategy to test a whole system?

Divide and conquer.

The pyramid

Push tests down. A bug caught by a unit test costs minutes; the same bug caught end-to-end costs an afternoon.

From an object-oriented point of view, what is the smallest testable part?

A class and its methods.

An object is a cohesive set of data and behaviour — that is exactly a unit.

Which methods deserve a test?

A pragmatic filter

MethodTest it?Why
Constructor with invariantsYesIt is where invalid state gets in
Business logicYesThis is the actual product
Trivial getterNoNothing to break
Generated equalsNoYou did not write it
Private helperIndirectlyThrough the public method that uses it

If a private method is complex enough to need its own test,

it probably wants to be its own class.

Part three

Testing in isolation

Can you test a class that depends on three other classes?

Two strategies

Test A and B together

  • Tests A, B and their interplay
  • Fewer moving parts to write
  • When it fails, which one is broken?
  • B might be slow, or a network

Test A in isolation

  • Replace B with a double
  • Failure points at A
  • Fast and deterministic
  • You must know B's contract

A test double

Why doubles exist

  • Isolate the unit under test
  • Remove slow or unreliable dependencies (network, clock, filesystem, terminal)
  • Reach states that are hard to produce for real
  • Break the dependency between two teams working in parallel

Stub or mock? They are not synonyms.

The distinction

Stub

Provides canned answers.

  • You assert on the result
  • state verification
  • “Given the mail service says OK, the order is complete”

Mock

Pre-programmed with expectations.

  • You assert on the interaction
  • behaviour verification
  • “The order asked the mail service to send”

A stub, by hand

class MailServiceStub implements MailService {
    private final List<Message> sent = new ArrayList<>();

    @Override public void send(Message msg) { sent.add(msg); }
    public int messagesSent() { return sent.size(); }
}

@Test
void unfilledOrderSendsMail() {
    MailServiceStub mailer = new MailServiceStub();
    Order order = new Order(mailer);

    order.fill(emptyWarehouse);

    assertEquals(1, mailer.messagesSent());   // state verification
}

A mock, with Mockito

@Test
void unfilledOrderAsksMailerToSend() {
    MailService mailer = mock(MailService.class);
    Order order = new Order(mailer);

    order.fill(emptyWarehouse);

    verify(mailer).send(any(Message.class));  // behaviour verification
    verifyNoMoreInteractions(mailer);
}

Stubbing return values with Mockito

Warehouse warehouse = mock(Warehouse.class);
when(warehouse.hasInventory("sword", 1)).thenReturn(true);
when(warehouse.hasInventory("shield", 1)).thenReturn(false);

Order order = new Order("shield", 1);
order.fill(warehouse);

assertFalse(order.isFilled());

when stubs. verify mocks. Most tests want when.

Do not mock what you do not own.

Mock your interfaces. Wrap third-party APIs first, then mock the wrapper.

How do you test a game that draws to a terminal?

You do not draw

  • Put an interface between your code and Lanterna: GUI
  • Production: LanternaGUI implements GUI
  • Tests: mock(GUI.class), then verify(gui).drawHero(...)
  • This single abstraction is worth more marks than any feature you will add

Part four

Continuous integration

Your tests pass. On your laptop. On Tuesday.

A test suite nobody runs is a comment.

CI is what makes running it involuntary.

A pipeline that fits on one slide

name: build
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '21' }
      - run: ./gradlew build jacocoTestReport
      - uses: actions/upload-artifact@v4
        with: { name: coverage, path: build/reports/jacoco }

Every push. Every pull request. No opinions involved.

What the pipeline should refuse to merge

  • A failing test
  • A drop in branch coverage below the agreed floor
  • New Checkstyle or SpotBugs violations
  • From week 11: a mutation score below the floor

Take away

  • Write the test first — it is a design activity, not a checking activity
  • Stubs verify state; mocks verify interaction
  • Isolate the terminal behind an interface you own
  • Green on CI, or it did not happen
