Patterns II

Creational patterns make objects. Structural patterns arrange them.

Behavioural patterns are about who talks to whom.

Strategy

Interchangeable algorithms

Three kinds of monster movement. Where does the choice live?

Strategy

interface MovementStrategy {
    Position nextPosition(Monster m, Arena a);
}

class ChasePlayer  implements MovementStrategy { ... }
class RandomWalk   implements MovementStrategy { ... }
class PatrolRoute  implements MovementStrategy { ... }

class Monster {
    private MovementStrategy movement;
    void setMovement(MovementStrategy m) { this.movement = m; }
    Position step(Arena a) { return movement.nextPosition(this, a); }
}

Behaviour becomes a field. It can change at runtime — a monster that panics at low health.

Strategy is Open/Closed made concrete.

You met the principle in week 6; this is what it looks like in the code.

Command

Requests as objects

What does it take to add undo to your game?

Command

interface Command {
    void execute();
    void undo();
}

class MoveHeroCommand implements Command {
    private final Arena arena;
    private final Direction direction;
    private Position previous;

    public void execute() {
        previous = arena.hero().position();
        arena.moveHero(direction);
    }
    public void undo() { arena.setHeroPosition(previous); }
}

What you get once requests are objects

  • Undo and redo — keep a stack of them
  • Key remapping — a Map<Key, Command>, configurable at runtime
  • Macros — a command that holds a list of commands (Composite again)
  • Replay and logging — the command history is the save file
  • Testability — a command is trivially unit-testable in isolation

Menus, keybindings and undo are the same problem.

Command is why.

Observer

One to many

The score changes. Five things on screen need to know. How?

Observer

interface ScoreListener { void scoreChanged(int newScore); }

class Score {
    private final List<ScoreListener> listeners = new ArrayList<>();
    private int value;

    public void add(int points) {
        value += points;
        listeners.forEach(l -> l.scoreChanged(value));   // notify
    }
    public void addListener(ScoreListener l) { listeners.add(l); }
}

The subject does not know what the listeners do. It only knows they exist.

Consequences

  • Subject and observers are loosely coupled — that is the point
  • The order of notification is undefined. Do not depend on it.
  • Cascading updates are hard to debug — a change can ripple
  • Forgetting to unregister is a memory leak
  • Every GUI framework you will ever use is built on this

State

An object with modes

Week 7's state machine. How does it become code?

State

abstract class GameState {
    abstract GameState processKey(Key key, Game game);
    abstract void draw(GUI gui);
}

class RunningState extends GameState {
    GameState processKey(Key key, Game game) {
        if (key == ESC) return new PausedState(this);
        arena.moveHero(key.toDirection());
        return this;
    }
}

class PausedState extends GameState {
    private final GameState resumed;
    GameState processKey(Key key, Game game) {
        return key == ESC ? resumed : this;
    }
}

No switch (currentState) anywhere. Each state knows only its own transitions.

State vs Strategy

Same shape

  • Both delegate to an interface
  • Both replace a conditional
  • UML diagrams are near-identical

Different intent

  • Strategy: the client picks. The object does not change itself.
  • State: the object transitions itself, driven by events.

Two more

Template Method & Iterator

Template Method

abstract class Level {
    public final void load() {          // final: the algorithm is fixed
        createTerrain();
        placeHero();
        placeMonsters();                // subclasses fill in the steps
        placeItems();
    }
    protected abstract void placeMonsters();
    protected void placeItems() { }     // optional hook
}

Factory Method is a Template Method whose step happens to create an object.

Iterator

class Arena implements Iterable<Element> {
    private final List<Element> elements;
    public Iterator<Element> iterator() { return elements.iterator(); }
}

for (Element e : arena) { e.draw(gui); }

Java gave you this one. Implement Iterable and the language cooperates.

Architecture

Putting it together

You have twelve classes and a game loop. Where does each one go?

Model · View · Controller

The three roles

  • Model — state and rules. Plain Java. No Lanterna, no keyboard, no screen.
  • Viewer — reads the model and draws it. Holds no game state.
  • Controller — takes input, changes the model, asks the viewer to redraw

If the Model imports Lanterna, the design has failed.

That single import is the difference between a testable project and an untestable one.

The game loop

public void run() throws IOException {
    while (state != null) {
        gui.clear();
        state.draw(gui);
        gui.refresh();

        Action action = gui.getNextAction();
        if (action == Action.QUIT) break;
        state = state.step(this, action);       // State pattern
    }
    gui.close();
}

Every pattern from this week is visible in twelve lines.

Take away

  • Strategy: the client chooses. State: the object transitions.
  • Command turns menus, keybindings, undo and replay into one mechanism
  • Observer decouples, and makes debugging harder — both are true
  • The Model must compile without the GUI. Test it by removing the dependency.
