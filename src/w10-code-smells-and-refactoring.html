Quality

Smells and refactoring

Your project works and the tests are green. Is the code good?

“It works” is not a quality standard.

It is the entry requirement.

Any fool can write code that a computer can understand. Good programmers write code that humans can understand.

Martin Fowler

What is a code smell?

A surface indication that usually corresponds to a deeper problem.

Not a bug. Not always wrong. Always worth a second look.

The catalogue

Smells you will find in your own project

Bloaters

  • Long method — if you need a comment to explain a block, extract it
  • Large class — too many fields, too many reasons to change
  • Long parameter list — four or more; usually a missing object
  • Primitive obsession — int x, int y everywhere instead of Position
  • Data clumps — the same three values travelling together, always

Primitive obsession, and its cure

// before
void moveHero(int x, int y) { ... }
boolean isInside(int x, int y) { ... }
double distance(int x1, int y1, int x2, int y2) { ... }

// after
void moveHero(Position p) { ... }
boolean isInside(Position p) { ... }
double distance(Position a, Position b) { ... }

You cannot pass a width where a height was expected once they have types.

Object-orientation abusers

  • Switch statements on type — polymorphism is asking to be used
  • Refused bequest — a subclass that overrides parent methods to do nothing
  • Temporary field — a field only set during one algorithm
  • Alternative classes with different interfaces — same job, incompatible names

Couplers

  • Feature envy — a method more interested in another class's data than its own
  • Inappropriate intimacy — two classes that know each other's internals
  • Message chains — a.getB().getC().getD().doThing()
  • Middle man — a class that only delegates

Feature envy

// in class Renderer
void draw(Hero hero) {
    int x = hero.getPosition().getX();
    int y = hero.getPosition().getY();
    int hp = hero.getHealth();
    int max = hero.getMaxHealth();
    double ratio = (double) hp / max;      // this is Hero's business
    ...
}

// Hero should answer the question
double healthRatio() { return (double) health / maxHealth; }

Move the behaviour to the data. That is what objects are for.

Dispensables

  • Duplicated code — the original sin; every other smell is downstream of it
  • Dead code — delete it. Git remembers.
  • Speculative generality — an abstraction for a requirement that never came
  • Comments — sometimes deodorant sprayed on bad naming

Are comments a smell?

It depends on the comment

Deodorant

// check if hero is alive and
// has not left the arena
if (h.hp > 0 && a.in(h.p)) {

Extract a well-named method instead.

Valuable

// Lanterna reports the terminal size
// one row short on macOS; see #142
height = terminal.getRows() + 1;

Explains why. The code cannot.

The cure

Refactoring

Refactoring: changing the internal structure

without changing the observable behaviour.

Without a test suite, it is not refactoring.

It is just editing and hoping.

The discipline

  • Start green
  • Make one small transformation
  • Run the tests
  • Commit
  • Repeat. If you are ever more than five minutes from green, back out.

Refactorings worth knowing by name

RefactoringApplies to

RenameEverything. The most valuable and most neglected.

Replace conditional with polymorphism

// before
int damage(Monster m) {
    switch (m.getType()) {
        case CHASER:  return 10;
        case FLYER:   return 5;
        case BOSS:    return 30;
        default:      return 0;
    }
}

// after
interface Monster { int damage(); }
class Chaser implements Monster { public int damage() { return 10; } }
class Boss   implements Monster { public int damage() { return 30; } }

Adding a monster now touches zero existing files.

Your IDE does most of this for you.

Rename, Extract Method, Introduce Parameter, Change Signature — learn the four shortcuts.

When do you refactor?

Three good moments, one bad one

  • Before adding a feature — make the change easy, then make the easy change
  • After getting it green — the third step of TDD
  • When you read it and had to think twice
  • Not as a two-week “refactoring sprint” with the suite red

Measuring

Static analysis

Tools that find smells for you

  • SonarQube / SonarCloud — smells, duplication, complexity, coverage in one report
  • PMD — rule-based; good at long methods and dead code
  • SpotBugs — bytecode analysis; finds real bugs, not just style
  • IntelliJ inspections — already running, already ignored

The report asks which smells remain in your code.

“None” is not a credible answer. Knowing which ones, and why you left them, is.

Take away

  • A smell is a hint, not a verdict
  • Move behaviour to the data it uses
  • Refactoring without tests is editing and hoping
  • Small steps, green at every commit
