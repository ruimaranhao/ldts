Quality

How good are your tests?

Your suite has 92% branch coverage. How many bugs would it catch?

Coverage tells you what was executed.

It says nothing about what was checked.

92% coverage, zero verification

@Test
void gameRuns() {
    Game game = new Game(new Arena(20, 10));
    game.step(Action.UP);
    game.step(Action.DOWN);
    game.step(Action.LEFT);
}
// green, high coverage, and it would pass if step() did nothing at all

So how do you test the tests?

Break the code on purpose.

If the suite stays green, the suite is not doing its job.

Mutation testing

Fault injection, automated

The idea

How it runs

  • The tool makes small changes to your bytecode — mutants
  • For each mutant, it runs the tests that cover that line
  • Test fails → the mutant is killed. Good.
  • All green → the mutant survived. Your suite missed it.
  • Mutation score = killed / total

Typical mutation operators

OperatorExample
Conditionals boundarya > b → a >= b
Negate conditionalsa == b → a != b
Matha + b → a - b
Incrementsi++ → i--
Void method callsremove the call entirely
Return valuesreturn x → return null

PIT in the Gradle build

plugins { id("info.solidsoft.pitest") version "1.15.0" }

pitest {
    junit5PluginVersion = "1.2.1"
    targetClasses = setOf("com.ldts.game.model.*")
    mutators = setOf("STRONGER")
    timestampedReports = false
    mutationThreshold = 70          // fail the build below this
}

./gradlew pitest → build/reports/pitest/index.html

Read the surviving mutants, not the score.

Each survivor is a line number and a missing assertion.

What survivors usually mean

  • You executed the line but asserted nothing about its effect
  • You asserted on the wrong thing — a count instead of a value
  • The mutated code is genuinely equivalent (rare, and worth writing down)
  • The line is dead and should be deleted

Cost and how to live with it

  • It is slow — every mutant is a test run
  • Target the model package only; do not mutate the Lanterna adapter
  • Run it nightly on CI, not on every push
  • In the project: a mutation report is required. A score above 70% on the model is the bar.

Property-based testing

Stop inventing examples

How many example tests would it take to be confident in Position.translate?

Example tests check the cases you thought of.

That is precisely the set that excludes your bugs.

The shift

  • Stop writing: for input 3, expect 4
  • Start writing: for all inputs, this property holds
  • The framework generates hundreds of inputs, including the nasty ones
  • When it fails, it shrinks the input to the smallest failing case

A property, with jqwik

import net.jqwik.api.*;

class PositionProperties {

    @Property
    void translateThenBackIsIdentity(@ForAll int x, @ForAll int y,
                                     @ForAll @IntRange(min=-50, max=50) int dx,
                                     @ForAll @IntRange(min=-50, max=50) int dy) {
        Position start = new Position(x, y);

        Position there = start.translate(dx, dy);
        Position back  = there.translate(-dx, -dy);

        assertThat(back).isEqualTo(start);
    }
}

jqwik is a JUnit 5 engine. Same build, same ./gradlew test, no new language.

Constraining the domain

@Property
void heroNeverLeavesArena(@ForAll("arenas") Arena arena,
                          @ForAll Direction direction) {
    arena.moveHero(direction);
    assertTrue(arena.isInside(arena.hero().position()));
}

@Provide
Arbitrary<Arena> arenas() {
    return Combinators.combine(
            Arbitraries.integers().between(3, 40),
            Arbitraries.integers().between(3, 40))
        .as(Arena::new);
}

This one property replaces about twenty example tests — and finds the corner you forgot.

Properties worth looking for

  • Round trip — encode then decode returns the original
  • Invariant — something that is true after every operation
  • Idempotence — doing it twice is the same as once
  • Commutativity — order does not matter
  • Oracle — agrees with a slow, obviously-correct implementation

Two kinds of test, both needed

Example

  • Documents one concrete behaviour
  • Readable as a specification
  • Fast, deterministic
  • Only finds what you predicted

Property

  • Documents a general rule
  • Explores inputs you would not
  • Shrinks failures automatically
  • Harder to write; some code has no obvious properties

Take away

  • Coverage measures execution; mutation testing measures verification
  • A surviving mutant is a missing assertion with a line number
  • Properties test rules, examples test cases — write both
  • Target mutation at the model, not at the adapter
