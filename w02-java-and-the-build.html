Part one

Java, for people who already program

You know C and C++. What is genuinely different here?

The short version

C++Java
MemoryYou free itGarbage collected
CompilationTo machine codeTo bytecode, then JIT
InheritanceMultipleSingle, plus many interfaces
PointersYes, arithmetic and allReferences only, no arithmetic
GenericsTemplates, compile-time expansionErasure — type info is gone at runtime
Header filesYesNo

There are only two kinds of value in Java.

Primitives, and references to objects. Everything follows from that.

Value vs reference

Primitives and references

int a = 5;              // a *is* 5
int b = a;              // b is a copy

int[] xs = {1, 2, 3};   // xs is a *reference* to an array
int[] ys = xs;          // ys points at the same array
ys[0] = 99;
System.out.println(xs[0]);   // 99

Why is == wrong for Strings?

The trap

String a = "hero";
String b = "hero";
System.out.println(a == b);        // true  -- both interned

String c = new String("hero");
System.out.println(a == c);        // false -- different objects
System.out.println(a.equals(c));   // true  -- same characters

The first case is only true because of the string pool. Do not rely on it.

== compares identity. equals compares value.

For every object you write, you decide what “equal” means.

The equals/hashCode contract

  • If a.equals(b) then a.hashCode() == b.hashCode()
  • The converse is not required — collisions are legal
  • Break this and your objects vanish inside a HashSet
  • Override both, or neither. Never one.

Records give you both for free

public record Position(int x, int y) {
    public Position translate(int dx, int dy) {
        return new Position(x + dx, y + dy);
    }
}
// equals, hashCode, toString and accessors are generated
// and the object is immutable

Use records for value objects. You will want Position in the project.

Collections you will actually use

  • List<T> — ordered, duplicates allowed (ArrayList)
  • Set<T> — no duplicates (HashSet, LinkedHashSet)
  • Map<K,V> — key to value (HashMap)
  • Deque<T> — queue or stack (ArrayDeque)
  • Program to the interface, construct the implementation

Program to the interface

List<Element> walls = new ArrayList<>();   // yes
ArrayList<Element> bad = new ArrayList<>(); // no

// swapping the implementation later costs one line, not fifty

Interface or abstract class?

The rule of thumb

interface

  • A capability: Drawable, Movable
  • A class can implement many
  • No state
  • Your default choice

abstract class

  • A partial implementation to share
  • A class can extend only one
  • Can hold state
  • Use when there is real shared code

Both, together

public interface Drawable {
    void draw(GUI gui);
    default boolean isVisible() { return true; }   // default method
}

public abstract class Element implements Drawable {
    private Position position;
    protected Element(Position position) { this.position = position; }
    public Position getPosition() { return position; }
}

Exceptions

  • Checked — declared, caller must handle: IOException
  • Unchecked — programming errors: NullPointerException, IllegalArgumentException
  • Throw unchecked for “the caller made a mistake”
  • Never catch (Exception e) {}. An empty catch block is a lie.

try-with-resources

try (Screen screen = terminalFactory.createScreen()) {
    screen.startScreen();
    gameLoop(screen);
}   // close() is called for you, even if gameLoop throws

Part two

The build

Why not just press Run in IntelliJ?

Because the build has to run without you.

On a teammate's laptop. On a grading machine. On CI at 3am.

What a build system does

  • Compiles sources in the right order
  • Fetches and pins dependencies
  • Runs the tests
  • Produces a runnable artefact
  • Does all of it identically, every time, for everyone

Repetitive, with variations.

That is the definition of something a human should stop doing by hand.

The Gradle lifecycle

  • compileJava → processResources → classes
  • compileTestJava → test
  • jar → assemble
  • check → build
  • Tasks declare dependencies; Gradle works out the order and skips what is up to date

build.gradle.kts

plugins {
    java
    application
}

java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }

repositories { mavenCentral() }

dependencies {
    implementation("com.googlecode.lanterna:lanterna:3.1.2")
    testImplementation(platform("org.junit:junit-bom:5.10.2"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testImplementation("org.mockito:mockito-core:5.11.0")
}

application { mainClass = "com.ldts.game.Application" }

tasks.test { useJUnitPlatform() }

The commands

./gradlew build      # compile + test + assemble
./gradlew test       # tests only
./gradlew run        # run the application
./gradlew tasks      # what else can I do?
./gradlew clean      # when you no longer trust anything

Why ./gradlew and never gradle?

The wrapper pins the version.

Your build works on my machine because it downloads your Gradle, not mine.

Dependencies

  • implementation — needed to compile and run
  • testImplementation — needed only by tests
  • Coordinates are group:artifact:version
  • Pin exact versions. latest.release is how builds start failing on their own.
  • Transitive dependencies are pulled in for you — and so are their conflicts

Two libraries want different versions of the same dependency. Now what?

Conflict resolution

  • Gradle picks the highest version by default
  • ./gradlew dependencies shows you the resolved graph
  • You can force a version, or exclude a transitive one
  • When something breaks mysteriously after adding a library, look here first
